SparkRisk

Recorded trip timing review for Spark Shop & Deliver
How SparkRisk Works

What it does

Orders recorded Spark trips into a review queue by how far their elapsed time sits from a fixed reference. It is a triage aid, not a detector: timing alone does not establish fraud, a scam, or even a process problem. Picked and dispatched are statuses recorded by the source system, not verified register arrival or store exit.

What the score is (model v3.1)

  • Excess time compares trip duration against a fixed 60 seconds per item. That figure is an arbitrary reference constant. It has never been fitted to this store, these drivers, or any confirmed outcome.
  • Driver deviation compares the trip against the same driver’s earlier recorded trips at the same store, and needs at least 3 of them before it contributes anything.
  • Whichever components are available are normalised to 0–100. A session with no driver history is scored on excess time alone.
  • Peer comparison is not implemented. No peer source has been mapped, so the queue has no peer column and no peer term in the score.
  • History (none / limited / recorded) reports how many prior trips back the baseline. It is not a confidence that anything is wrong.

What it cannot tell you

Nothing here is calibrated against confirmed outcomes, because no shortage or audit-outcome source has been mapped yet. A high score means “look at this one first”, nothing more. Every finding still has to be established from video, order detail and the audit record.

Workflow

  1. Import normalized order records on the Import Data tab
  2. Work the queue from the top; the score only sets the order
  3. Click a session to inspect source timestamps, order details and review notes
  4. Resolve real order numbers when needed for investigation
  5. Record the outcome: cleared, confirmed, or escalated — with notes

Coverage

Baselines only see trips that have been imported. A driver active for months but imported for one day has one day of history, and the badge will say so.

Privacy & Security

All data stays in this browser's IndexedDB. Real order IDs and driver names are visible in the detail panel. There is no durable audit log — “Resolve real order numbers” only writes a line to the browser console, which is lost when the service worker sleeps. Treat everything here as unlogged access and never move extracted data outside authorized systems.

Import Order Data

Automatic WISMO extraction is not connected. Import a JSON array of normalized orders, or an object containing an orders array. Reimporting the same source updates those orders in place and rebuilds every trip — it never duplicates them, and saved review decisions are carried across.

Required: order_id, total_order_qty, pick_started_time and dispatched_time (ISO timestamps). Include store_nbr, driver_uuid or driver_id, trip_id, extraction_date, and picked_time when available. Raw API responses must first be normalized to these fields.
